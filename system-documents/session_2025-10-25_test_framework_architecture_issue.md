# Test Framework Architecture Issue

## Problem Statement

**Test files compile but produce invalid WASM with "function variable out of range" errors.**

Example: `31_testing_framework.wasm` has errors:
```
function variable out of range: 45 (max 43)
function variable out of range: 43 (max 43)
function variable out of range: 46 (max 43)
```

## Root Cause Analysis

### Current Compilation Pipeline

**For regular code:**
```
AST → Semantic Check → TAST → MIR → WASM (via MirCodeGenerator)
```

**For test blocks (`tests:`):**
```
AST → Semantic Check → ??? → WASM (via OLD CodeGenerator)
```

### The Problem

1. **Test blocks don't exist in HIR, TAST, or MIR**
   - No `TestsBlock` in `src/hir/mod.rs`
   - No `TestsBlock` in `src/typechecker/tast.rs`
   - No `TestsBlock` in `src/mir/mir_types.rs`

2. **Test blocks are only handled in:**
   - `src/semantic/mod.rs:2533` - Type checking only
   - `src/codegen/mod.rs:1119` - OLD CodeGenerator path
   - `src/codegen/statement_generator.rs:45` - OLD statement generator

3. **MirCodeGenerator wraps CodeGenerator:**
   ```rust
   // src/codegen/mir_codegen.rs:27
   pub struct MirCodeGenerator<'a> {
       wasm_generator: CodeGenerator,
       // ...
   }
   ```

4. **Function Registration Mismatch:**
   - User functions (add, multiply, etc.) are compiled via MIR
   - MIR assigns function indices: `wasm_generator.function_count + i`
   - Test framework expressions call these functions
   - BUT test expressions are generated by OLD CodeGenerator
   - OLD CodeGenerator might use stale/incorrect function indices

### Evidence

**File:** `tests/cln/testing/31_testing_framework.cln`

Contains:
- User-defined functions (lines 1-28): add, multiply, formatName, isEven, etc.
- Test block (lines 30-74): Calls these functions plus stdlib

```clean
tests:
    "adds two positive numbers": add(5, 3) = 8        // Calls user function
    "multiplies positive numbers": multiply(4, 3) = 12  // Calls user function
    string.length("hello") = 5                          // Calls stdlib
    math.sqrt(16.0) = 4.0                              // Calls stdlib
```

**What happens:**
1. MIR compiles `add`, `multiply`, etc. → assigns indices 40, 41, 42, 43
2. Test block tries to call `add` → OLD CodeGenerator generates Call(?)
3. Index mismatch → Invalid WASM

### Why This Occurs

Test blocks are **top-level statements** but MIR only handles **functions**:
- MIR `struct MirProgram` contains `functions: HashMap<SymbolId, MirFunction>`
- No field for top-level statements or test blocks
- Test blocks must be compiled separately from MIR

## Affected Files

5 test framework files fail WASM validation:
1. `31_testing_framework.wasm` - indices 43, 45, 46 (max 43)
2. `42_test_framework.wasm` - index 42 (max 42)
3. `100_testing_framework_simple.wasm` - index 42 (max 42)
4. `test_complex_onerror.wasm` - index 43 (max 43)
5. `test_final_onerror.wasm` - indices 43 (max 43)

## Solution Options

### Option 1: Migrate Test Framework to MIR (Recommended)

**Pros:**
- Proper architecture
- Eliminates OLD CodeGenerator usage
- Consistent compilation path

**Cons:**
- Requires MIR extension to support test blocks
- Significant refactoring

**Implementation:**
1. Add `TestBlock` to MIR types
2. Lower TAST test blocks to MIR
3. Generate test runner in MIR
4. Remove OLD test block codegen

### Option 2: Ensure CodeGenerator Synchronization (Quick Fix)

**Pros:**
- Minimal code changes
- Preserves current architecture

**Cons:**
- Maintains dual codegen paths
- Technical debt

**Implementation:**
1. Ensure test block generation uses the SAME `CodeGenerator` instance as `MirCodeGenerator.wasm_generator`
2. Register user functions in `function_map` before test block generation
3. Verify `function_count` is synchronized

### Option 3: Disable Test Block WASM Generation (Temporary)

**Pros:**
- Immediate fix
- No architecture changes

**Cons:**
- Removes functionality
- Not a real solution

**Implementation:**
1. Skip test block generation in WASM output
2. Only execute tests in interpreter mode
3. Document limitation

## Recommended Approach

**Short-term:** Implement Option 2 to fix the 5 failing files (+2.8% validation rate)

**Long-term:** Plan migration to Option 1 as part of compiler modernization

## Implementation Plan for Option 2

### Step 1: Trace the Code Path

Find where test blocks are generated and ensure they use the correct CodeGenerator instance.

**Check:**
- How does MirCodeGenerator interact with test blocks?
- Is there a separate instantiation of CodeGenerator for tests?

### Step 2: Verify Function Registration

Ensure all functions (MIR + stdlib) are registered in `function_map` before test generation.

**Check:**
- When are stdlib functions registered?
- When are MIR functions registered?
- When is test block generation triggered?

### Step 3: Fix Index Calculation

Update test block generation to use the correct function indices from `function_map`.

**Location:** `src/codegen/mod.rs:8804` (generate_tests_block_runner)

### Step 4: Test and Validate

Compile all 5 affected test files and verify WASM validation passes.

## Conclusion

This is an architectural issue where test blocks use a different compilation path than regular code. The immediate fix is to synchronize the CodeGenerator instances, but the proper long-term solution is to migrate test framework to the MIR pipeline.

**Impact:** Fixing this will improve validation rate from 57.1% to ~60% (5 additional files).
