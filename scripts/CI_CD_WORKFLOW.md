# COMITA - Automated CI/CD Workflow

Trigger: when the user types **"comita"**, execute this automated CI/CD workflow.

The authoritative step list (TASKS.md sweep, version bump, tag, push, CI wait, install, plugin rebuild, issue follow-up) is the legacy `comita` flow in the maintainer's global instructions; this page summarises it for this repository and documents the release gate.

## Workflow Loop

```
REPEAT until CI passes:
  1. Stage & commit changes with descriptive message
  2. Push to remote (and tags if version changed)
  3. Calculate wait time from recent CI runs
  4. Wait for CI with progress updates every 2 minutes
  5. Check CI status
  6. IF FAILED → get logs, analyze, fix, GOTO REPEAT
  7. IF PASSED → cleen install latest + cleen frame install latest, rebuild plugins, report success, EXIT
```

## Step 1: Commit, Bump and Tag

```bash
git add -A
git commit -m "fix: <auto-generated based on changes>"

# Bump the patch version in Cargo.toml, then amend it into the same commit
git add Cargo.toml Cargo.lock
git commit --amend --no-edit

VERSION=$(grep '^version' Cargo.toml | head -1 | sed 's/.*"\(.*\)"/\1/')
git tag "v$VERSION"            # tags are v-prefixed: release.yml triggers on 'v*'

git push && git push --tags
```

## Step 2: Calculate Wait Time

```bash
gh run list --workflow=CI --limit=3 --json startedAt,updatedAt | \
  python3 -c "
import json, sys
from datetime import datetime
runs = json.load(sys.stdin)
if runs:
    durations = []
    for r in runs:
        start = datetime.fromisoformat(r['startedAt'].replace('Z', '+00:00'))
        end = datetime.fromisoformat(r['updatedAt'].replace('Z', '+00:00'))
        durations.append((end - start).total_seconds())
    avg = sum(durations) / len(durations)
    print(int(avg + 60))
else:
    print(1020)
"
```

## Step 3: Wait and Monitor

- Wait for the calculated duration (~17 minutes typical)
- Check CI status every 30 seconds in the final 2 minutes

## Step 4: Check CI Results

```bash
gh run list --workflow=CI --limit=1 --json conclusion,status,number
```

## Step 5: Handle Results

**If CI PASSES:**
```bash
~/.cleen/bin/cleen install latest
~/.cleen/bin/cleen frame install latest
```
then rebuild the framework plugins from source with the new compiler and commit the rebuilt artifacts, as the global `comita` steps describe.

**If CI FAILS:**
```bash
gh run view <run-number> --log-failed
```
Then analyze the error, fix the issue, and repeat from Step 1.

## Release Gate

`.github/workflows/release.yml` (tag push) builds the binaries and calls
`.github/workflows/framework-gate.yml`. The `release` job needs both, so a
failed gate means no GitHub release and nothing for `cleen install latest`.
The gate also runs on every push to main. It:

1. builds `cln` + `wasmtime_runner` from the commit;
2. runs `scripts/check_regressions.py` (the `tests/cln/bugfixes` pins;
   pins that need a plugin are skipped here);
3. checks out `Ivan-Pasco/cleen-framework-old` (main), rebuilds every plugin
   with the new `cln`, installs them in a scratch `~/.cleen`, reruns the pins
   with the plugins present, then runs the framework suites, the plugin
   helper tests and `smoke-examples.sh` (`scripts/framework_gate.sh`).

The framework repo is public, so no secret is needed. If it is ever made
private, add a repository secret `FRAMEWORK_REPO_TOKEN` (read access to its
contents); without it the gate prints a warning and skips step 3.

Run the same gate locally before tagging:

```bash
scripts/framework_gate.sh --framework ../clean-framework \
  --cln target/release/cln --server ~/.cleen/bin/clean-server \
  --runner target/release/wasmtime_runner
```

When waiting for CI, watch the `Release Clean Language Compiler` run for the
tag. The other workflows also run: `CI`, `Architecture Guards`, `.cln corpus`,
`Coverage`, `Framework gate`, `regression pins` (pushes to main) and
`JSON property tests` (pull requests touching codegen/JSON). Only `fuzz.yml`
and `nightly.yml` are disabled (their schedules are commented out).

## Rules

- Always wait for CI to complete — never skip
- Always fix root causes when CI fails
- Always provide progress updates during wait
- Always use semantic versioning for tags, written `vX.Y.Z`
- Never assume CI passed without checking
